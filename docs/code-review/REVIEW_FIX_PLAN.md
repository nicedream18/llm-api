## 3. 第一批：授权、计费入口和响应策略

### REVIEW-001：MCP软件资源权限

- **最小方案：** 所有软件调用先得到规范化tool_id；同时验证mcp_tool与software execute；工具列表按资源权限过滤。
- **验收：** 同一非管理员分别走通用、命名与HTTP入口，无software grant均被拒绝；有grant可调用；仍需审批的工具不能靠approved参数绕过管理员审批。
- **回归：** 显式grant、资源通配grant、不同principal、禁用工具、禁用实例、列表元数据。
- **发布注意：** 对此前依赖过宽通用grant的Key会收紧权限，需列出授权差异供管理员确认，不能为兼容继续保留旁路。

### REVIEW-002：KB/RAG统一调用策略

- **最小方案：** 从HTTP/MCP到KB/RAG显式传AuthContext，LLM与embedding进入同一策略入口；独立记录每轮execution_id和token消耗。
- **验收：** 只允许cheap模型的Key不能请求expensive；allowed_channels在最终路由生效；耗尽配额时无上游调用；deep_research所有轮次与embedding都受预算限制。
- **回归：** KB read不等于任意模型执行权限；管理员与非管理员、Wiki既有问答路径、失败/取消/部分消耗。
- **依赖：** 可先阻止旁路，再与009接入可恢复结算；不应等待大规模重构才修复授权。

### REVIEW-003：响应扫描

- **最小方案：** 在客户端输出与日志落盘前使用sanitized_body；阻断与扫描失败的行为明确。为流式制定能够兑现的策略，暂不支持的组合应显式拒绝。
- **验收：** 合成秘密不出现在返回、日志或错误消息；跨SSE片段的命中不能绕过；fail_closed开启/关闭与mode均有确定结果。
- **约束：** 流式缓冲要有内存、响应大小和超时上限，不使用无限缓存；不能用每片独立正则假装完成跨片扫描。

## 4. 第二批：任务状态和配额恢复

### REVIEW-008 → REVIEW-007：先执行权，再幂等提交

1. 领取任务产生单调generation/fencing token，写入唯一执行owner；续租失败禁止再发布结果。
2. 所有失败/进度/完成及分块发布都校验owner、generation和有效lease；迟到写返回明确的“已失去执行权”。
3. 文本切分和embedding在事务外完成；事务内按文档版本发布完整分块、元数据和任务完成状态。使用稳定身份/唯一约束约束重放。
4. 线程取消采用协作停止；不能把asyncio任务取消等同于底层线程结束。

**验收矩阵：**

- A租约失效、B接管后，A的成功/失败/进度提交均不能影响B。
- 在分块提交、文档更新、KB统计与任务完成的每个边界注入失败，重试后恰好一套分块、正确统计。
- 重启恢复与重复投递不会重复发布；embedding失败不会先破坏仍可用的上一版本。
- 在隔离MySQL实例验证真实锁和竞争，不仅依赖SQLite。
- 升级存在旧Worker时要先停止旧执行或有兼容切换方案，避免旧进程仍绕开新fencing；这是后续部署动作，本轮未执行。

**已有数据：** 先只读盘点每个doc/version的重复分块、异常任务owner和索引generation，备份后制定独立修复方案；本次不自动去重、删除或重建用户数据。

### REVIEW-009：结算恢复

- **最小方案：** 持久化待结算execution、reserve、实际已知用量及终态；settle幂等；失败可重放并且重启可恢复；未知上游消耗单独标记。
- **验收：** 上游成功后settle失败，服务重启并恢复后额度与实际一致；重复恢复不会双扣；失败调用已有消耗时不能全额释放；租约/用量账本异常可审计。
- **回归：** SSE部分输出、客户端断开、多attempt均有实际消耗、估算与上游usage差异、配额不足与超额结算。
- **已有数据：** 先只读比对reserved、用量账本和已知请求状态；对未知消耗保守处理并记录依据，不直接把所有reserved设为released。

## 5. 第三批：MCP和协议契约

### REVIEW-010：参数只规范化一次

- 将原始参数与内部执行描述区分，router不再把包装后的结果送回同一个规范化函数。
- HTTP回归覆盖software.<id>.<name>与invoke_software_tool、required/additionalProperties、审批和001的授权组合。
- 验收同时断言实际连接器收到的参数与原始业务字段相同，而非只断言HTTP200。

### REVIEW-004、005：工具消息完整性

- 建立共用的规范消息/事件映射，分别修复StreamCodec和AnthropicAdapter路径；不是仅修改一个converter后假设其他入口自动生效。
- 必测：纯文本、纯工具、多工具并行、工具参数分片、文本与工具混合、tool_result、ID/name/arguments保留、正确stop_reason和usage。
- 覆盖OpenAI↔Anthropic、OpenAI↔Responses的项目承诺方向；未支持的方向给出明确错误。
- 先做无网络契约测试，再用受控Provider/真实客户端验收；不以模拟返回代替厂商兼容结论。

### REVIEW-006：完成与截断

- 定义每种协议的成功结束证据；EOF仅结束传输，不补造业务成功。
- 验收“文本后EOF”“半个JSON事件”“错误事件后断流”“正常finish/usage尾帧”“用户取消”五类路径。
- 客户端事件、attempt、usage、quota、日志的最终状态一致；已经输出内容后不得无幂等保障地重放请求。

## 7. 修复后的交付门禁

1. 以本报告复现为基础添加有断言的行为回归，先证明修复前失败、修复后通过；避免只测试实现细节。
2. 运行完整后端、前端、类型和静态门禁；维持现有全局/关键模块覆盖基线，同时补关键状态分支。
3. 在新建隔离MySQL测试环境验证任务fencing、配额结算、刷新租约、迁移升级/中断恢复。生产连接不用于测试。
4. 真实Provider与部署浏览器验收分别记录环境、请求协议、结果及未通过项，不能将skip算pass。
5. 在受控环境验证Docker健康检查、冷启动、停机与升级恢复，检查后台任务和连接关闭。
6. Linux上验证同步/流式混合请求与共享HTTP客户端生命周期；本轮未复现的跨循环疑点仍需证据，不能直接记作已修复Bug。
7. 每批复审只包含必要业务/测试/迁移变更，保留回退策略与数据核对记录；有用户未提交修改时逐项保护。
